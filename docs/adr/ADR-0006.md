# ADR-0006: DirectConnection для autotune_stop

## Статус

Принято

## Дата

2026

## Контекст

GUI общается с `GpuWorker` (всё в отдельном QThread) преимущественно через
сигналы со слотами, чтобы все вызовы IGCL и состояние воркера жили в одном
потоке. Вкладка «Авторазгон» (`tabs/autotune.py`) инициирует поиск
синхронным вызовом в потоке воркера; отмена — сигнал `stop_requested`.
Возник вопрос: подключать его через обычную queued-связь или напрямую.

## Решение

`stop_requested` подключается к `worker.autotune_stop` через
`Qt.ConnectionType.DirectConnection` (`window.py`). Причина: во время поиска
воркер-поток *занят* синхронным алгоритмом (`autotune/engine.py`) и не обрабатывает
очередь событий Qt — queued-слот сработал бы только после завершения поиска,
т.е. отмена была бы бессмысленной.

Сам слот `autotune_stop` лишь присваивает `self._autotune_stop = True`;
движок проверяет этот флаг через `stop_check` на итерациях. Присваивание bool
потокобезопасно под GIL (атомарная операция над CPython-объектом), отдельных
примитив синхронизации не требуется.

Это задокументированное исключение из общего правила «всё через очереди»:
исключение введено, обосновано и ограничено одним флагом отмены.

## Плюсы

- Отмена срабатывает немедленно, а не по концу поиска — авторазгон реально
  управляем пользователем.
- Реализация тривиальна: один bool под GIL, без QMutex и таймаутов.
- Правило проекта «потокобезопасность через GIL + один владелец состояния»
  сохраняется.

## Минусы

- Нарушает единообразие «все сигналы → воркер — queued»: исключение надо помнить
  и объяснять новым контрибьюторам (поэтому и записано в этом ADR).
- Присваивание bool безопасно только пока флаг — скалярный CPython-объект;
  расширение этого паттерна на сложные структуры без локов было бы ошибкой.
